# Feature workflow with Jarvis and Codex

Jarvis creates the issue in `Draft` with only the scope requested by Edgar. Edgar approves that exact scope revision; Jarvis records the approval and marks the issue `ready`. Codex then executes the complete flow: Requirements Analyst (Gherkin) → Architect → Developer → Reviewer → QA. Scope approval authorizes this flow within scope, without a second Gherkin approval or new authorization between phases. Required UI review, SQL changes, publication, merge, and deployment retain their explicit approval gates.

## Issue as the feature record

The supplied GitHub issue in this repository is the canonical record. Jarvis supplies its URL/number, exact approved scope revision, and Edgar's approval evidence when launching Codex; a direct Codex request must identify the same record. Confirm the repository, issue body, comments, approval, and labels. A label alone is not approval evidence. If the issue or approval is missing, inaccessible, locked, or ambiguous, report BLOCKED to Jarvis and leave the phase unclaimed. Codex must not create or select another issue or use local feature files as a fallback.

Codex authors and posts complete requirements, design, Developer and Reviewer handoffs, QA plan/results, and the feature record as **separate Markdown issue comments**. Use [`_template`](_template/) as content guides only; do not create new `features/FEAT-NNN/` files or implementation logs. The Codex coordinator owns the feature record (state evidence, decisions, approvals, handoffs, and verification summary). Each role owns its phase artifact. Jarvis coordinates Edgar's decisions and launches Codex; it does not draft or publish Codex's artifacts.

Preserve all historical feature records, including FEAT-007, and their decisions and approvals. Do not move, delete, or reinterpret them under the new flow. For continued historical work, read and link prior files and put new phase output on the supplied issue.

Start comments with headings such as `## Requirements — issue #123 — revision 1`, `## Design`, `## Developer handoff`, `## Reviewer handoff`, `## Test plan and results`, or `## Feature record`. Include issue, role, status/result, approved scope reference, and exact input comment/code revisions. Record the permalink, numeric comment ID, and content revision: an ID alone cannot distinguish edits to a draft. Preserve full Markdown, including Gherkin and QA tables; summaries do not replace artifacts.

Codex rereads comments before posting to avoid duplicates, then reads back its own posted artifact to verify the body and reports its permalink, ID, and revision. If posting or verification fails, stop the phase, report BLOCKED to Jarvis, and do not proceed to the next phase. Jarvis must not draft or post the artifact on Codex's behalf. At each gate, the Codex coordinator posts and verifies a new feature record linking governing artifacts and the previous record.

An author may edit their own draft before handoff after rereading it and preserving the full replacement body; report its ID and new content revision. For handed-off requirements, reviewed code, QA results, or other gate-affecting changes, **append a new versioned comment** linking the superseded one. Keep prior evidence. Gherkin corrections or additions within approved scope need no second approval from Edgar; record their consistency with scope and propagate the new revision through affected downstream phases. A material scope change stops affected work for Edgar's approval through Jarvis, unless Edgar expressly delegated that decision for this feature. Record the delegation, its limits, and the authorized decision; never infer it. Code changes after review need Reviewer and QA again, plus required UI review. Record decisions against exact scope, comment, and code revisions.

## Posting and updating comments

Codex uses an available issue-comment connector. If it cannot create normal comments, Codex may use an authenticated GitHub client or REST: `GET /repos/{owner}/{repo}/issues/{issue_number}/comments`, `POST /repos/{owner}/{repo}/issues/{issue_number}/comments` with a Markdown `body`, or `PATCH /repos/{owner}/{repo}/issues/comments/{comment_id}` with the full replacement body for its own draft. The comment ID is **not** the issue number. Check `html_url` and read back the body. CLI: `gh issue comment ISSUE --repo OWNER/REPO --body-file PATH`; prefer comment-ID operations for exact edits. If authentication, posting, or read-back is unavailable, stop and report BLOCKED to Jarvis; there is no Jarvis publication fallback. Do not put tokens in files or comments.

## Claiming authorized work

Analyst runs first while the issue is `ready`, publishing and verifying Gherkin within approved scope. **Architect** then verifies Edgar's exact approved scope and approval evidence, the published requirements comment/revision, their consistency, issue identity, and current labels. Separate approval of the Gherkin comment is not required. Before design, Architect adds `inprogress`, removes `ready`, and fetches the issue to confirm `inprogress` present and `ready` absent. Preserve unrelated labels with additive add-label and single-label removal operations. REST: `POST /repos/{owner}/{repo}/issues/{issue_number}/labels` with `{"labels":["inprogress"]}`, then `DELETE /repos/{owner}/{repo}/issues/{issue_number}/labels/ready`. CLI: `gh issue edit ISSUE --repo OWNER/REPO --add-label inprogress --remove-label ready`. Codex records and verifies the claim in its feature record comment.

If `ready` is absent, both labels exist, or the issue is already `inprogress`, check claim history. Resume only a matching authorized run for the same issue, approved scope, and governing requirements revision; otherwise report BLOCKED to Jarvis. If a label operation fails, reread the issue, report the exact partial state, and stop before design until the intended state is verified. The claim preserves scope authorization; it does not authorize expansion or bypass other gates.

## Handoffs and gates

1. **Requirements Analyst** (`pm_requirements_analyst`) reads approved scope on the ready issue and posts complete requirements. Every observable acceptance criterion belongs in a Gherkin `Scenario` or `Scenario Outline` with `Given`, `When`, `Then`, a unique `@AC-NN` tag, and concrete outcomes. Cover a normal path and relevant rejection/exception path; explain if none applies. Keep prose for context and scope. Verify the posted comment and its consistency with scope, then hand off to Architect without another approval of in-scope Gherkin.
2. **Architect** (`pm_architect`) verifies scope and requirements, performs and verifies `ready` → `inprogress`, then posts and verifies design: affected files, data/UI impact, risks, and verification strategy. Codex continues to Developer after this handoff without separate design approval within scope.
3. **Developer** (`pm_developer`) reads the verified claim, requirements, and design, implements scope, adds appropriate tests, and posts and verifies its handoff with files, checks, limits, and exact code revision/artifact.
4. **Reviewer** (`pm_reviewer`) independently reviews that revision against scope, requirements, and design, may correct code/tests within scope, and posts and verifies findings, corrections, checks, and final revision for QA. Material scope changes follow the approval/delegation rule above.
5. **QA** (`pm_qa`) posts and verifies test plan/results with at most six focused cases by default. Each case cites a governing `@AC-NN` scenario; each scenario has a case or explicit BLOCKED coverage gap. Run permitted checks against the final reviewed revision and record PASS, FAIL, or BLOCKED with evidence per case. Defects return to Developer, then Reviewer, then QA on the new revision. Unrun cases cannot be PASS.

The Codex coordinator verifies each handoff and continues the complete flow until QA and any required owner gate, stopping at a failed gate. Each role performs its phase; the coordinator invokes the next role. Architect's claim is the only role-driven issue-label transition here. Phase completion does not authorize SQL/migrations, publication, deployment, push, PR creation, or merge. Edgar retains required UI review, merge, and deployment approvals. Jarvis marks `completed` only when Edgar explicitly confirms the feature is finished; QA PASS, technical review, or merge alone is insufficient.

## States

| State | Gate |
| --- | --- |
| `Draft` | Jarvis created the issue with only requested scope; Edgar's approval is pending. No Codex implementation starts. |
| `Ready` (`ready`) | Edgar approved the exact scope revision and Jarvis marked ready. Codex starts Analyst and proceeds through the full flow; Gherkin is produced after ready. |
| `In Progress` (`inprogress`) | After verified Gherkin, Architect verified scope and changed `ready` to `inprogress` before design. Developer, Reviewer, and QA follow verified handoffs. |
| `UI Review` | QA passed and `ui_review: required`; Edgar can interact with a private, temporary preview of the exact revision. |
| `In Review` | QA passed, required UI review was approved by Edgar, and the revision awaits any required PR, merge, or deployment approval. |
| `Completed` (`completed`) | Edgar explicitly confirmed the feature is finished; Jarvis recorded that confirmation and marked completed. Preserve applicable UI, merge, and deployment approval/evidence. |

When `ui_review: none`, explain why and move from QA PASS to `In Review`. A visible UI change invalidates prior UI approval. A final code revision change requires QA and any required UI review again. Technical review never replaces Edgar's approval. UI review uses a clickable, private, temporary preview with synthetic data and an exact revision reference. Do not use an existing SQL database without checking its destination and obtaining required authorization. Record a blockage if no safe preview is available. Do not publish a preview or PR, merge, or deploy without authorization. Preserve historical state names and approvals in historical records.

## Jarvis activation

Jarvis starts a **Codex task** after scope approval and marking ready, on the owner's connected computer or configured Codex cloud environment. Supply repository, issue URL/number, exact approved scope revision and approval evidence, any express delegation, and existing run/handoff references for a resume. Codex coordinates the entire flow with project-scoped `.codex/agents/pm_*.toml` roles. Use each actual `agent_type`; a renamed generic agent does not load its instructions. Jarvis's background agents are not these roles.

Before starting, Codex checks `git rev-parse --show-toplevel`, `git status --short --branch`, all five available role types, and issue/comment read/write access. Verify scope approval and ready state (or matching resume). Preserve local changes and checkout. If a required capability or gate is missing, report BLOCKED to Jarvis and leave the phase unclaimed. Do not fall back to generic agents, local feature files, or Jarvis-authored artifacts.

Codex invokes Analyst → Architect → Developer → Reviewer → QA, waits for each result, verifies the posted artifact and governing revision, and reports links, evidence, and blockages to Jarvis. Do not wait for a new launch or Edgar approval between successful phases within scope. Before retrying an uncertain launch, Jarvis checks for an existing task and comments for the same issue, scope, and phase. This repository does not install or change monitors, Dot triggers, or Jarvis permissions; the earlier read-only scanning pilot remains historical.
