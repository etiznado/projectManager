# Feature workflow with Jarvis and Codex

Jarvis creates the issue in `Draft` with only the scope requested by Edgar. Edgar approves that exact scope revision; Jarvis records the approval and marks the issue `ready`. Codex then executes the complete flow: Requirements Analyst (Gherkin) → Architect → Developer → Reviewer → QA. Scope approval authorizes this flow within scope, without a second Gherkin approval or new authorization between phases. Required UI review, SQL changes, publication, merge, and deployment retain their explicit approval gates.

## Issue decisions and Codex evidence

The supplied GitHub issue in this repository is the canonical record. Jarvis supplies its URL/number, exact approved scope revision, and Edgar's approval evidence when launching Codex; a direct Codex request must identify the same record. Confirm the repository, issue body, comments, approval, and labels. A label alone is not approval evidence. If the issue or approval is missing, inaccessible, locked, or ambiguous, report BLOCKED to Jarvis and leave the phase unclaimed. Codex must not create or select another issue or use local feature files as a fallback.

The same publication rule applies to Jarvis-launched work and manually started Codex chats. Keep only these items on the issue:

- Approved scope and acceptance criteria, including Analyst's tagged Gherkin and necessary in-scope criterion revisions.
- Approved scope changes, with Edgar's decision or the explicit delegation and its limits.
- Blockers requiring Edgar's intervention, stating the decision/action needed and affected work.
- One final Codex summary: what was implemented, what was verified, what is pending, and available PR/evidence links.

Do not post startup comments, routine phase handoffs, repeated confirmations, full logs, extensive artifacts, or a coordinator record at every gate. Design, Developer/Reviewer handoffs, full QA plan/results, logs, and detailed state/verification evidence stay in Codex or, when useful and authorized, in the PR. A phase failure goes to the coordinator for correction; publish a blocker only if Edgar must intervene. Internal handoffs do not require issue publication or a publication check. The final summary must distinguish verified work from pending or blocked work; it does not replace the detailed evidence.

Each role authors its own complete phase artifact. The Codex coordinator retains state evidence, decisions, approvals, and artifact references in Codex or the PR, verifies each handoff, and invokes the next role. Jarvis coordinates Edgar's decisions and launches Codex; it does not draft or publish Codex's artifacts. Do not create new `features/FEAT-NNN/` files or implementation logs. Preserve historical records, including FEAT-007 and existing issue comments; do not move, delete, rewrite, or reinterpret them. For continued historical work, link prior records and apply this publication rule to new output.

Use [`_template`](_template/) as content guides only. **Known conflict:** their legacy instructions require full design/QA artifacts and coordinator records as issue comments. Apply the publication rule above while retaining their useful content in Codex or the PR; those templates remain unchanged. Document incompatible instructions found in other files or a monitor in Codex or the PR, without modifying them outside approved scope. Do not change monitor behavior or automate chat startup as part of this rule.

## Artifact references and revisions

Every handoff identifies the issue, role, status/result, exact approved scope and approval evidence, governing requirements/design revisions, and exact code revision/artifact. For issue content, retain permalink, numeric comment ID, and content revision; an ID alone cannot distinguish edits. For Codex or PR artifacts, retain a retrievable message/artifact reference or PR link and an explicit content revision, plus the exact code revision when applicable. The receiving role and coordinator read the actual artifact and verify consistency, completeness, and the governing revision before continuing. Missing or unverifiable input stops the affected phase; do not replace detailed artifacts with an unsupported summary.

Authors may revise their own draft before handoff after rereading it. After handoff, retain the previous artifact and append a new version with its superseded reference **in the same permitted destination**: acceptance criteria on the issue, design/handoffs/QA evidence in Codex or the PR. Gherkin corrections or additions within approved scope need no second approval from Edgar; record their consistency with scope and propagate the new revision through affected downstream phases. A material scope change stops affected work for Edgar's approval through Jarvis (or directly in a manual chat), unless expressly delegated for this feature. Record the delegation, its limits, and the authorized decision; never infer it. Preserve the approved change and its authority on the issue. Code changes after review need Reviewer and QA again, plus required UI review. Record decisions against exact scope, artifact, and code revisions.

## Posting and updating comments

Before an allowed publication, reread the issue/comments to avoid duplicates; existing scope or criteria need no confirmation comment. Codex uses an available issue-comment connector. If it cannot create normal comments, Codex may use an authenticated GitHub client or REST: `GET /repos/{owner}/{repo}/issues/{issue_number}/comments`, `POST /repos/{owner}/{repo}/issues/{issue_number}/comments` with a Markdown `body`, or `PATCH /repos/{owner}/{repo}/issues/comments/{comment_id}` with the full replacement body for its own draft. The comment ID is **not** the issue number. Check `html_url`, read back the body, and retain its permalink, ID, and content revision in Codex. CLI: `gh issue comment ISSUE --repo OWNER/REPO --body-file PATH`; prefer comment-ID operations for exact edits. If a required publication or its verification fails, stop affected work and report BLOCKED to Jarvis or Edgar in Codex; there is no Jarvis publication fallback. Do not post test-access or read-back confirmation comments. Do not put tokens in files or comments.

## Claiming authorized work

Analyst runs first while the issue is `ready`, recording and verifying acceptance Gherkin within approved scope on the issue. **Architect** then verifies Edgar's exact approved scope and approval evidence, the requirements comment/revision, their consistency, issue identity, and current labels. Separate approval of the Gherkin comment is not required. Before design, Architect adds `inprogress`, removes `ready`, and fetches the issue to confirm `inprogress` present and `ready` absent. Preserve unrelated labels with additive add-label and single-label removal operations. REST: `POST /repos/{owner}/{repo}/issues/{issue_number}/labels` with `{"labels":["inprogress"]}`, then `DELETE /repos/{owner}/{repo}/issues/{issue_number}/labels/ready`. CLI: `gh issue edit ISSUE --repo OWNER/REPO --add-label inprogress --remove-label ready`. Codex records and verifies the claim in Codex or the PR, without a claim/feature-record comment on the issue.

If `ready` is absent, both labels exist, or the issue is already `inprogress`, check claim history. Resume only a matching authorized run for the same issue, approved scope, and governing requirements revision; otherwise report BLOCKED to Jarvis. If a label operation fails, reread the issue, report the exact partial state, and stop before design until the intended state is verified. The claim preserves scope authorization; it does not authorize expansion or bypass other gates.

## Handoffs and gates

1. **Requirements Analyst** (`pm_requirements_analyst`) reads approved scope on the ready issue and records acceptance criteria there, reusing existing valid criteria instead of duplicating them. Every observable acceptance criterion belongs in a Gherkin `Scenario` or `Scenario Outline` with `Given`, `When`, `Then`, a unique `@AC-NN` tag, and concrete outcomes. Cover a normal path and relevant rejection/exception path; explain if none applies. Reference existing scope instead of copying it; keep extended analysis in Codex or the PR. Verify issue criteria and scope consistency, then hand the exact requirements revision to Architect without another approval of in-scope Gherkin.
2. **Architect** (`pm_architect`) verifies scope and requirements, performs and verifies `ready` → `inprogress`, then authors and verifies design in Codex or the PR: affected files, data/UI impact, risks, and verification strategy. Codex continues to Developer after this handoff without separate design approval within scope.
3. **Developer** (`pm_developer`) reads the verified claim, requirements, and design, implements scope, adds appropriate tests, and provides a verified handoff in Codex or the PR with files, checks, limits, and exact code revision/artifact.
4. **Reviewer** (`pm_reviewer`) independently reviews that revision against scope, requirements, and design, may correct code/tests within scope, and provides verified findings, corrections, checks, and final revision for QA in Codex or the PR. Material scope changes follow the approval/delegation rule above.
5. **QA** (`pm_qa`) authors and verifies the full test plan/results in Codex or the PR with at most six focused cases by default. Each case cites a governing `@AC-NN` scenario; each scenario has a case or explicit BLOCKED coverage gap. Run permitted checks against the final reviewed revision and record PASS, FAIL, or BLOCKED with evidence per case. Defects return to Developer, then Reviewer, then QA on the new revision. Unrun cases cannot be PASS.

The Codex coordinator verifies each handoff and continues the complete flow until QA and any required owner gate, stopping at a failed gate. Each role performs its phase; the coordinator invokes the next role. Record this verification internally, without routine issue comments. At the end of the authorized run, Codex posts and reads back one final issue summary with implemented/verified/pending work and available PR/evidence links; do not claim completion while an owner gate remains. Architect's claim is the only role-driven issue-label transition here. Phase completion does not authorize SQL/migrations, publication, deployment, push, PR creation, or merge. Edgar retains required UI review, merge, and deployment approvals. Jarvis marks `completed` only when Edgar explicitly confirms the feature is finished; QA PASS, technical review, or merge alone is insufficient.

## States

| State | Gate |
| --- | --- |
| `Draft` | Jarvis created the issue with only requested scope; Edgar's approval is pending. No Codex implementation starts. |
| `Ready` (`ready`) | Edgar approved the exact scope revision and Jarvis marked ready. Codex starts Analyst and proceeds through the full flow; Gherkin is produced after ready. |
| `In Progress` (`inprogress`) | After verified Gherkin, Architect verified scope and changed `ready` to `inprogress` before design. Developer, Reviewer, and QA follow verified handoffs. |
| `UI Review` | QA passed and `ui_review: required`; Edgar can interact with a private, temporary preview of the exact revision. |
| `In Review` | QA passed, required UI review was approved by Edgar, and the revision awaits any required PR, merge, or deployment approval. |
| `Completed` (`completed`) | Edgar explicitly confirmed the feature is finished; Jarvis recorded that confirmation and marked completed. Preserve applicable UI, merge, and deployment approval/evidence. |

When `ui_review: none`, explain why and move from QA PASS to `In Review`. A visible UI change invalidates prior UI approval. A final code revision change requires QA and any required UI review again. Technical review never replaces Edgar's approval. UI review uses a clickable, private, temporary preview with synthetic data and an exact revision reference. Do not use an existing SQL database without checking its destination and obtaining required authorization. Record a blockage if no safe preview is available. Do not publish a preview or PR, merge, or deploy without authorization. Preserve historical state names and approvals in historical records.

## Activation through Jarvis or a manual chat

Jarvis starts a **Codex task** after scope approval and marking ready, on the owner's connected computer or configured Codex cloud environment. Supply repository, issue URL/number, exact approved scope revision and approval evidence, any express delegation, and existing run/handoff references for a resume. Codex coordinates the entire flow with project-scoped `.codex/agents/pm_*.toml` roles. Use each actual `agent_type`; a renamed generic agent does not load its instructions. Jarvis's background agents are not these roles.

In a manually started chat, Codex uses the same supplied issue, scope authorization, roles, independent reviews, tests, approval gates, publication limits, and artifact verification. Record direct owner decisions and any expressly authorized feature-specific exception against the exact scope; do not generalize an exception to later features.

Before starting, Codex checks `git rev-parse --show-toplevel`, `git status --short --branch`, all five available role types, and issue/comment read/write access, without posting a probe comment. Verify scope approval and ready state (or matching resume). Preserve local changes and checkout. If a required capability or gate is missing, report BLOCKED to Jarvis or Edgar in Codex and leave the phase unclaimed; use an issue blocker only when Edgar's intervention is needed. Do not fall back to generic agents, local feature files, or Jarvis-authored artifacts.

Codex invokes Analyst → Architect → Developer → Reviewer → QA, waits for each result, verifies the actual artifact and governing revision in its permitted destination, and reports detailed links, evidence, and technical blockages in Codex or the PR. Do not wait for a new launch or Edgar approval between successful phases within scope. Before retrying an uncertain launch, check for an existing Codex task and its internal handoffs as well as the issue's scope, criteria, and decision history; absence of routine issue comments is not evidence that no run exists. This repository does not install or change monitors, Dot triggers, or Jarvis permissions; the earlier read-only scanning pilot remains historical.
